## When to use

- To confirm that an action worked when its result is not in view: **SB-341 archived**.
- To say that an action failed, with `error`, when the user can try again.

## When not to use

- For a decision. Use a [Modal](?path=/docs/feedback-modal--docs).
- For an error in a form field. Show it at the field.
- For something the user must read later. A toast goes away.

## Usage

Toast shows a message; it does not time itself out or stack itself. The app keeps the list, puts
the toasts in one [ToastStack](?path=/docs/feedback-toaststack--docs), and removes each after a
timer.

## Interaction test

**Show toasts (test)** checks that each action adds a toast to the one stack, that the error toast
has its style, and that the focus stays on the button that was pressed. CI runs it in the built
Storybook.

## Accessibility

- A toast never takes focus, so the user's place is kept.

- A toast is a `status`, an error toast an `alert`, so a screen reader reads it when it appears.
- The fade-in runs only when the system allows motion (`motion-safe`).

- [ToastStack](?path=/docs/feedback-toaststack--docs) is a live region, built on Base UI's toast
  viewport. Keep it mounted, and a screen reader reads each toast the app adds to it.
- Toast is Bob's own element, not Base UI's Toast.Root. Base UI's toast takes its content from a
  toast manager and is a `dialog`; Bob's Toast keeps its props and its roles.
