## When to use

- To confirm that an action worked when its result is not in view: **SB-341 archived**.
- To say that an action failed, with `type: 'error'`, when the user can try again.

## When not to use

- For a decision. Use a [Modal](?path=/docs/feedback-modal--docs).
- For an error in a form field. Show it at the field.
- For something the user must read later. A toast goes away.

<DoDont>
<Do>

- Write two to five words, past tense, no subject: **Title updated**, **SB-341 archived**.
- Let an error stay until the user acts. Bob does this by default: `toast.add({ title: 'Could not save', type: 'error' })`.
- Give every toast a `title`. It names the toast for a screen reader; TypeScript requires it.

</Do>
<Dont>

- Toast an action whose result the user can already see.
- Pass `priority`. Bob reads `type`: an error is read at once, a success when the screen reader is idle.

</Dont>
</DoDont>

## Usage

A toast is a call, not an element. Render one [ToastStack](?path=/docs/feedback-toaststack--docs)
at the root of the app, then add toasts in one of two ways. The API is Base UI's.

A manager, to add a toast from anywhere, also outside React:

```tsx
// toast.ts
export const toast = createToastManager();

// App.tsx
<ToastStack toastManager={toast}>
  <App />
</ToastStack>

// anywhere
toast.add({ title: 'Title updated' });
toast.add({ title: 'Could not save', description: err.message, type: 'error' });
```

The hook, in a component inside the stack:

```tsx
function SaveButton() {
  const toast = useToastManager();
  return <Button onClick={() => toast.add({ title: 'Saved' })}>Save</Button>;
}
```

- `toast.add` returns the toast's id. `toast.close(id)` closes it, and `toast.update(id, { title })` changes it.
- A success closes itself after the stack's `timeout` (4 seconds), or its own. An error stays until the user closes it, unless it has its own `timeout`. `timeout: 0` keeps any toast open.
- `toast.promise(promise, { loading, success, error })` shows one toast through the three states.

## Accessibility

<Keys rows={[
  ['F6', 'Moves focus to the stack and pauses the timers.'],
  ['Tab', 'In the stack: moves from the newest toast (at the bottom) upward, each toast then its Close button.'],
  ['Shift+Tab', 'From the stack: gives focus back to where it was before F6.'],
  ['Escape', 'Closes the focused toast.'],
  ['Enter Space', 'On Close: closes the toast.'],
]} />

- A toast never takes focus, so the user's place is kept.
- A screen reader reads each toast once. ToastStack keeps two live regions beside the stack, never inside it: polite for a success, assertive for an error. The stack itself is not a live region.
- The pointer over the stack, or focus in it, pauses the timers. A swipe down or to the right closes a toast.
- The fade-in runs only when the system allows motion (`motion-safe`).
- A screen reader test (VoiceOver, NVDA) is still to do before 1.0.0. The tests check the DOM: one live region per toast, and no live role inside a live region.
